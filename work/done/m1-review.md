# m1-review

**Objetivo.** Uma pessoa confere, à mão e no navegador, que o Marco 1 cumpre o parágrafo dele, cláusula por cláusula, e cada cláusula que falha ou que nenhuma entrega atende vira uma linha nova na fila.

**O parágrafo.** docs/06, Marco 1: "Quando ele fecha, uma bibliotecária consegue cadastrar livros, seus exemplares e membros, emprestar um exemplar a um membro por 21 dias e registrar a devolução; um membro com um livro atrasado ou com a inscrição suspensa é recusado."

**Comportamento.**
* A revisão pega o parágrafo cláusula por cláusula (docs/05 §8): cadastrar livros; seus exemplares; membros; emprestar um exemplar a um membro por 21 dias; registrar a devolução; um membro com um livro atrasado é recusado; um membro com a inscrição suspensa é recusado.
* Para cada cláusula, a página escreve, numa tabela em "O que aconteceu": a cláusula, a entrega que a atende (`work/done/<slug>.md`), o teste à mão passo a passo no navegador com o `npm run dev` (o que clicar, o que digitar, o que tem de aparecer, com os textos literais do docs/03 e das telas) e a coluna do resultado, vazia: "a testar pela pessoa".
* Os testes à mão formam uma sequência só, a partir de um banco vazio, então as matrículas e os números dos exemplares são previsíveis; um bloco "Preparação" diz, a partir de um clone novo, os comandos exatos e como começar do banco vazio, igual no Windows, no macOS e no Linux.
* A cláusula do atraso não tem relógio de teste no `npm run dev` (docs/01 §Ambientes): o teste dá o comando exato que recua as datas de um empréstimo aberto no banco, com o servidor parado, um `node -e` com o `node:sqlite`, que roda igual nos três sistemas.
* Uma cláusula que nenhuma entrega atende é um achado já na tabela; uma que falha nas mãos da pessoa é um achado depois do teste. Cada achado vira uma linha `[ ]` no Marco 1 do docs/06, abaixo da linha `m1-review`, esperando o /propose (docs/05 §8).
* A revisão não revisa código e não corrige nada.

**Contrato.** Nenhum. Nenhum código, migração, teste, rota ou configuração muda.

**Fora do escopo.**
* Revisão de código: docs/05 §8 diz que a revisão não revisa código.
* Corrigir o que o teste achar: cada achado é uma entrega própria, com a sua página (docs/05 §8).
* Testes automáticos novos: os e2e de cada entrega já provam o que é automático; esta revisão é a mão da pessoa.
* O que não está no parágrafo (multas, OD-1; email, OD-2; reservas; renovações): docs/00 §Não é.
* Capturas de tela: a revisão não cria tela.

**Pronto quando.**

* [x] Cada entrega da tabela aponta para um `work/done/<slug>.md` que existe.
* [x] O bloco "Preparação" tem os comandos de um clone novo e o jeito de começar do banco vazio, nos três sistemas.

**Escolhas feitas sem a pessoa.**
* O atraso é provocado recuando as datas no arquivo do banco, e não pelo cabeçalho `x-hoje`: o `npm run dev` nunca liga o relógio de teste (docs/01 §Ambientes, ADR-0005), e ligá-lo seria mudar configuração, o que a revisão não faz.
* O membro atrasado e o membro suspenso são pessoas diferentes: `podePegarEmprestado` olha a suspensão antes do atraso, então um membro com os dois mostra só "A sua matrícula está suspensa.".
* O teste das recusas no navegador vê primeiro a tela, que usa `podePegarEmprestado` para apagar o botão; a recusa do servidor com a tela parada entra como um passo do teste da suspensão, com duas abas.

**O que aconteceu.**

`npm run verify` verde no commit `9301f40` do `main` (o worktree `../biblioteca-m1-review`, depois de um `npm ci`): typecheck, lint, 148 testes unitários em 15 arquivos, 40 e2e, build. Nenhum servidor ficou rodando; o banco `data/biblioteca.sqlite` não foi criado nem tocado. Os comandos `node -e` abaixo foram rodados contra um banco descartável com as três migrações: o de recuar as datas mudou o empréstimo de `2026-10-02`/`2026-10-23` para `2026-09-02`/`2026-09-23`, o da data escreveu `23/10/2026`, o de apagar removeu o arquivo.

Nenhuma cláusula ficou sem entrega. A `esqueleto` não atende uma cláusula sozinha: é a base de todas (o `npm run dev`, o cabeçalho com os links "Catálogo", "Membros", "Empréstimos"). O parágrafo não tem outra cláusula além das sete; "o exemplar fica livre" e "por 21 dias" são testados dentro da devolução e do empréstimo.

*Preparação.* Num terminal, na pasta em que o repositório vai ficar; os comandos são os mesmos no PowerShell, no cmd, no Terminal do macOS e no bash do Linux.

1. `node --version` diz `v24` ou maior (`engines` do `package.json`). No Node 24, os comandos com `node:sqlite` podem escrever um `ExperimentalWarning`; ele não muda nada.
2. `git clone <endereço do repositório> biblioteca` e `cd biblioteca` (ou use a pasta do worktree, `../biblioteca-m1-review`).
3. `npm ci`. O `npx playwright install chromium` não é preciso para o teste à mão: só o `npm run verify` e o `npm run e2e` usam o navegador do Playwright.
4. Começar do banco vazio: com o servidor parado, na raiz do repositório, `node -e "require('node:fs').rmSync('data/biblioteca.sqlite', { force: true })"`. Num clone novo o arquivo não existe e o comando não faz nada; o próximo `npm run dev` cria o arquivo e aplica as migrações `0001-catalogo.sql`, `0002-membros.sql` e `0003-emprestimos.sql`, que o terminal nomeia.
5. `npm run dev`, e abra `http://localhost:5173` no navegador. Para parar o servidor: Ctrl+C no terminal do `npm run dev`, que encerra o cliente e o servidor juntos (no Windows, se aparecer "Terminate batch job (Y/N)?", responda `Y`).

Os testes são uma sequência só, na ordem da tabela, a partir do banco vazio: as matrículas (1, 2, 3) e os exemplares (1, 2, 3) saem nessa ordem. Os exemplos de data supõem o teste feito em 02/10/2026; noutro dia, a data de devolução de um empréstimo novo é hoje mais 21 dias, e `node -e "const d = new Date(); d.setDate(d.getDate() + 21); console.log(d.toLocaleDateString('pt-BR'))"` a escreve.

O teste no navegador vê a tela, que apaga "Emprestar" com `podePegarEmprestado`; quem impõe a regra é o servidor (docs/02), e a prova automática dele são `src/features/emprestimos/rota.server.test.ts` (o `409` de `TemLivrosEmAtraso` e de `MembroSuspenso`) e `eventosDeEmprestimo.test.ts`. O passo (4) da suspensão é o único em que a pessoa vê o servidor recusar sozinho.
